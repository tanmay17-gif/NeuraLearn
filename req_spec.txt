REQUIREMENTS SPECIFICATION
Stateful User Profiling Module for Personalized Video Summarization
Prepared by: Meenakshi Amit Paul  |  Research Scholar, Faculty of Computer Science, Pacific Academy of Higher Education and Research University, Udaipur
1. Purpose of This Document
This document specifies the exact requirements for a software module I need built as part of my doctoral research. It defines what the module must do, what it must not do, how it will be tested, and what must be delivered. Please read Section 8 (Scope Boundaries) carefully — it is as important as the requirements themselves.
Please do not add features beyond what is listed here. Additional functionality makes the module harder to document and defend academically.
2. Background and Context
This module is one component of a larger doctoral research project on personalized video summarization. The research problem is that existing video summarization systems produce the same generic summary for every user, and do not remember a user's preferences between sessions.
The module specified here solves the memory part of that problem. It stores what a user prefers, updates those preferences based on feedback, and converts the stored preferences into a natural-language instruction (a “prompt prefix”) that will later be used to guide an AI model.
Important: this module does NOT call any AI model itself. It only prepares the instruction text. A separate component (not part of this work) will consume that text.

FR-2: Core Storage Functions
The module must expose these four functions:
create_profile(user_id)  ->  creates new profile with defaults
get_profile(user_id)  ->  returns complete profile as a dict
update_profile(user_id, changes)  ->  updates fields, increments version
get_profile_history(user_id)  ->  returns list of past profile states
Every call to update_profile must increment profile_version by 1, update last_updated, and write a snapshot to the history table.
FR-3: Persistence Across Sessions
Profiles must survive program restart. If a profile is created, the program is closed completely, and then reopened, the profile must be retrievable with identical values.
FR-4: Multiple Independent Users
The module must support multiple users simultaneously. Two users must be able to hold entirely different preference values with no interference between them.
FR-5: Profile Change History
A separate history table must record every change with the following fields:
history_id, user_id, profile_snapshot (JSON), trigger_event, timestamp
This is a mandatory requirement, not optional. The history is required as research evidence showing that preferences evolved over time.
FR-6: Feedback-Driven Update Mechanism
The module must implement a function:
apply_feedback(user_id, rating, comment)  ->  updates profile per rules below
The update rules must be implemented exactly as specified in this table, and must be written as an explicit, readable rules structure (for example a dictionary or config block) rather than being scattered through conditional statements:

Rules must be easy to modify without changing program logic, since the rule set will be revised during research.
FR-7: Prompt Builder Function
The module must expose:
build_prompt(user_id)  ->  returns a natural-language instruction string
This function reads the CURRENT profile and converts it into readable English instruction text. Example mappings:
summary_length = short + style = bullets  →  “Produce a concise, bullet-point summary.”
detail_level = 2  →  “Keep explanations brief and avoid extended background.”
topics_of_interest = [AI, finance]  →  “Prioritise content relating to AI and finance.”
learned_behaviors indicates prior “too long” feedback  →  “This user has previously found summaries too long; keep output brief.”
The output must be plain readable English, not a data dump of field values. Different profiles must produce visibly different instruction text.
FR-8: Prompt Logging
Every call to build_prompt must be logged to a table with these fields:
log_id, user_id, profile_version_used, generated_prompt_text, timestamp

The module will be considered complete only when all of the following tests pass. Please run these and share the results.

Test T6 is the single most important test. It demonstrates that the system is stateful — that stored feedback changes future behaviour. Please provide the two prompt strings side by side as output.

9. Notes for Whoever Builds This
Simplicity is more valuable than sophistication here. The logic must remain explainable in a thesis and defensible in an oral examination.
Avoid frameworks that hide the update logic (for example, prebuilt LLM “memory” modules). The update mechanism must be visibly my own design.
Keep the rules in FR-6 separate from program logic so they can be revised without restructuring the code.
Please note the versions of Python and any packages used, for reproducibility.
